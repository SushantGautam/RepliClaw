## 1. Research questions

Verbatim from `EXPERIMENT_PROTOCOL_V2.md` §"Research Questions" [4]:

- **RQ1.** Does evidence-escrow EESS improve failure diagnosis versus the open-sharing swarm (S4) at matched budget?
- **RQ2.** What is the cost of centralization (S3 vs S4/S5) in diagnostic accuracy and budget consumption?
- **RQ3.** Which ablations (no-escrow, random selection, no counterfactual, single-agent) cause the largest regressions?
- **RQ4.** Do results transfer to a second, different case (Tox21) at the same budget?

## 2. Falsifiable predictions

Each prediction is stated so that a **negative result is a publishable, expected-capable answer** (SEED_PROMPT "negative results are publishable and expected").

- **P1 (escrow value, RQ1/S5 vs S4).** At matched envelope (identical tokens/wall/agents), EESS (S5) matches or beats the open-sharing swarm (S4) on the primary metric M1 (correct diagnosis rate, §7), with no budget overrun on either side. *Falsified if:* S5's M1 is below S4's M1 on the primary case beyond the run-to-run noise floor defined in §8 (i.e., no credible interval overlap favoring S5). A falsification is reported as: "open sharing already suffices on this case; escrow adds cost without diagnostic value here" — a complete, honest finding.
- **P2 (centralization cost, RQ2/S3 vs S5).** The adaptive central manager (S3) is not strictly more accurate than S5, or it is more accurate at higher diagnostic latency (median cycle time) or higher token consumption per correct diagnosis (M11). *Falsified if:* S3 strictly dominates S5 on both M1 and M9 latency at equal or lower M6 tokens per run. Falsification is reported as: "centralization pays on this case at matched budget" — also a complete finding.
- **P3 (ablation regressions, RQ3).** Removing escrow (A1), randomizing role selection (A3), or removing counterfactual testing regresses M1 relative to S5, in the order: escrow-removal ≥ random-selection ≥ counterfactual-removal. *Falsified if:* any ablation equals or beats S5 on M1. A falsification identifies which mechanism was load-bearing (or was not) — equally useful.
- **P4 (transfer, RQ4/S5 on Tox21).** The ranking S5 ≥ S4 ≥ A1 holds on the secondary Tox21 case under the same per-arm envelope class. *Falsified if:* the ranking inverts on Tox21. Falsification is reported as: "escrow benefit does not transfer to multi-label toxicity adjudication" — a boundary condition for the mechanism, publishable as such.

If all four are falsified, the honest summary is: "on these cases at this budget, no EESS mechanism is demonstrated; S3/S4 baselines are the recommendation." That is a valid result for this competition entry.

### 5.2 Parity mechanism (what "matched budget" proves)

Mechanism owner: P05 @ `7fa4f68`, `.worktrees/p05/src/repliclaw/comparators/budget.py`:
1. **Single frozen envelope hash.** All arms in a run are constructed with the identical `BudgetEnvelope` instance; its `sha256()` is recorded in `run_metadata.json`. A parity violation (different envelope hashes across arms of the same case) fails the run — `test_parity_requires_same_envelope` (P05, 19 passing red-first tests).
2. **Hard abort at the envelope.** `BudgetLedger.record()` raises `BudgetOverflow` the moment cumulative tokens/wall/agents exceed the ceiling; the harness aborts the arm mid-run and marks it `aborted_budget` — it cannot silently overrun. `test_ledger_budget_overflow_enforced` covers this. This is the **hard enforcement** the mission requires: the harness, not the model, aborts.
3. **Parity assertion after the run.** `assert_budget_parity(runs)` passes only if all non-aborted runs of the case used the same envelope hash and none exceeded it. The report must include the per-arm ledger table (tokens, wall, agent-seconds) so a reader can verify parity from artifacts, not from claims.

**Honest semantics (declared explicitly):** parity of *envelope* (identical ceiling + no overrun) is what the mechanism proves. It does **not** prove equal *consumption* — arms may legitimately consume different amounts within the same ceiling (that is a scientific outcome, measured as M6/M7, not a parity failure). If the P05 budget-parity *test suite* (the 19-test package) has not been re-verified on the merged run tree by window start, the mechanism spec above is the contract the test must satisfy, and the reference is marked **`[PENDING: P05 re-verification on merged tree]`** (guard S3, §9.3).

### 5.3 Budget ledger accounting

Tokens are counted at the harness layer from API usage fields (per `EESS_CONTRACTS` §7 artifact contract; P05 ledger API). Wall time is monotonic, measured from arm start to verdict. If a provider omits a usage field, that call is **excluded from the campaign** (the run is invalidated, not estimated) — no fabricated token counts.

## 6. Metrics (exact denominators)

Unit of analysis: one **run** = one arm on one case, executing its protocol to verdict or budget abort. `N_run = 20` (primary, per arm), `N_run = 10` (secondary, per arm).

| ID | Metric | Definition (exact) | Denominator |
|----|--------|--------------------|-------------|
| **M1** | **Primary — correct diagnosis rate** | Fraction of runs whose final verdict matches the sealed oracle on both defect class and target artifact (policy_rag_v1: `retrieval_omission` on the returns-policy retrieval path). Secondary (Tox21): per P06 oracle schema, defined at case-landing. | denominator = `N_run` **per arm** (20 primary / 10 secondary); never pooled across arms. |
| **M2** | Falsification discipline | Fraction of preregistered hypotheses that the run actually attempted to falsify (had a recorded intervention or counterfactual slot). | denominator = number of hypotheses registered by the arm during the run (arm-defined, recorded in `final_verdict.json`); reported as per-run then per-arm mean. |
| **M3** | Counterfactual yield | Fraction of counterfactual slots executed that produced a verdict change or a falsified hypothesis. | denominator = number of counterfactual slots granted (S5/A1/A3); S0/S3/S4 report `n/a` (no slots by design). |
| **M4** | Leakage incidents | Count of oracle references in arm-side code/paths during the run (re-grep per `EESS_CONTRACTS` §6 at teardown). | denominator = number of runs; any count > 0 voids the affected run (and triggers stopping rule S5). |
| **M5** | Budget consumption (tokens) | Total ledger tokens per run. | per run; reported per arm as mean + range. |
| **M6** | Efficiency — tokens per correct diagnosis | Mean M5 over runs where M1 = 1. | denominator = correct runs per arm; `n/a` if zero correct runs (that itself is a result, reported as such). |
| **M7** | Budget overrun/abort rate | Fraction of runs ending in `aborted_budget`. | denominator = `N_run` per arm. Any arm with abort rate > 25% fails the window for that arm (S1, §9.1) and its envelope-adequacy is a report finding. |
| **M8** | Integrity-rejected artifacts | Count of artifacts rejected by escrow on integrity failure (S5/A3 only; A1 has no escrow). | per run; reported per arm mean. |
| **M9** | Latency to verdict | Wall seconds from arm start to sealed verdict. | per run; per-arm median + IQR. |
| **M10** | Verdict stability | Fraction of runs whose verdict matches the arm's modal verdict across the 20-run block. | denominator = `N_run` per arm. |
| **M11** | Correct-falsified-hypothesis rate | Fraction of preregistered hypotheses that were both falsifiable **and** correctly falsified (oracle-consistent) when the arm ran a falsification attempt. | denominator = number of preregistered falsifiable hypotheses with an attempted falsification, per run. This is the metric the mission names: "fraction of hypotheses correctly falsified per run". |

Primary metric: **M1** (S5 vs S4, RQ1). Secondary metrics: M11, M3, M6, M7, M9. All metrics are computed by the offline scorer only (no arm may compute its own score).

## 7. Runs, statistical plan

### 7.1 Runs per arm and honest justification

- Primary case: **20 runs per arm** (6 arms → 120 runs). Secondary: **10 runs per arm** (60 runs).
- **Justification (resource-constraint statement, NOT a power analysis):** the live window (§10) is bounded by the competition schedule and by the master ceiling in §5.1; 20 × 6 × ~2,600-tokens-observed-floor runs fit with > 10× headroom under the 60k envelope, while 20 runs/arm is the smallest count that lets M10 (stability) and M7 (abort rate) be non-trivial (a 1/20 abort = 5% visible, not a single-sample artifact). We do **not** claim this is powered for any specific effect size; the report will say so. `DECISION-2` (judge may reduce to 10/arm primary, which descope-declares M10 as unreliable rather than hiding it).
- Run-to-run variance control: identical case files, identical envelope, identical model endpoint settings (below); LLM sampling is **not** seed-controllable at the endpoint (declared), so run-to-run variance on live calls is an inherent property of the experiment and is exactly what M10/M2 capture. Deterministic components (engine, interventions, scoring, A3's random ranking) use fixed seeds (§11.2).

### 7.2 Statistical plan (pre-registered, no post-hoc choice)

- **Unit of analysis:** the case, not the run. With **n_cases = 1** for the primary comparison, **no inferential test is reported** for S5-vs-S4 on the primary case; the primary comparison is **descriptive** (point estimates + 95% CIs) with run-level bootstrap only as a within-case uncertainty device. This is a declared limitation, not a power claim.
- **Bootstrap (within-case):** 10,000 resamples of runs, seeded `20261010` (the harness seed), per arm; report arm-level M1 as point estimate with percentile 95% CI from the bootstrap; the S5-vs-S4 difference is reported with its bootstrap CI. *Decision rule (pre-registered):* "supports P1" ⟺ the difference CI's lower bound > 0; "inconclusive" ⟺ 0 ∈ CI; "falsifies P1" ⟺ upper bound < 0. No p-value is the decision basis.
- **Case-level inference (RQ4, when Tox21 lands):** with n_cases = 2, the *only* inferential statement allowed is a sign-consistency check across the two cases for each ranking claim (e.g., S5 ≥ S4 in both cases), reported descriptively. **No paired t-test, no McNemar, no effect-size inference across 2 cases** — any such number would be over-claiming; the feasibility-stage McNemar (p = 0.009, F05) belongs to the *feasibility* artifact, not to this prereg's conclusions.
- **Aborting as missing data:** `aborted_budget` runs are reported in M7 and **excluded** from M1 denominators with the exclusion stated per arm (not pooled away). Sensitivity analysis: recompute M1 including aborts as failures; report both.
- **One-sided vs two-sided:** N/A for the primary (descriptive). The pre-registered decision rule above is effectively one-sided for "supports" and two-sided for "falsifies"; the report must state which branch fired.
- **Alpha:** not applicable (no NHST on primary). For the case-level sign check, none is claimed. `DECISION`-free: this plan is fixed; the judge approves or rejects it wholesale (REVIEW Q6).

## 8. Stopping rules and counterevidence handling

### 8.1 Stopping rules (pre-registered; trigger → action)

| ID | Observation (objective, checkable) | Scope | Action |
|----|-----------------------------------|-------|--------|
| **S0** | Any arm's M7 abort rate > 25% within its first 10 runs | That arm, that case | Stop the arm for that case; record remaining runs as `not_run_stopped_S0`; report the envelope as inadequate for that arm (a finding, not a fix-and-continue). Envelope resize requires prereg v1.1. |
| **S1** | Any **leakage incident** (M4 > 0) | Whole campaign | Stop all runs; quarantine the affected case directory; write an incident record to `docs/experiments/incidents/`; no further runs until root cause is in the record and (if continuing) prereg amendment signed. Leakage evidence is **preserved in full**, never deleted. |
| **S2** | Endpoint unreliability: > 10% of API calls in any 30-minute window fail or time out | Campaign | Pause; log; resume after 2 consecutive clean 30-minute windows; if the window (§10) is exhausted, terminate with partial-run reporting (partial results are reported, clearly labeled `partial`, never silently dropped). |
| **S3** | Parity mechanism broken: any non-aborted run with an envelope hash differing from the case's frozen hash, or any overrun | Whole case | Invalidate the case block; do not re-run within this window (re-running after a mechanism failure would be post-hoc); report as mechanism failure. |
| **S4** | **Counterevidence to our own mechanism exceeding the pre-registered noise floor:** S5's M1 below S4's M1 with bootstrap difference CI upper bound < 0 on the primary case, **and** the pattern confirmed in the first 10-run interim (to avoid acting on 10-run noise) | Campaign | **Do not stop silently.** The run continues to completion (the negative *is* the result), then the campaign report leads with the falsification of P1, preserves all S5 artifacts verbatim, and states the boundary conditions under which escrow did not help. This is the mission's counterevidence rule made operational: counterevidence is preserved, reported first, and never hidden. |
| **S5** | Any arm producing a verdict the scorer cannot parse against the oracle schema (2 consecutive runs) | That arm | Stop the arm; its M1 reported as 0/`n` with `unscorable` reason attached; the bug is fixed **only** if the scorer is at fault (scorer bugs are harness bugs: fix, re-run the *same* sealed artifacts, record the re-score — never re-run the LLM). |

### 8.2 Counterevidence preservation (mandatory)

- Every run's full artifact tree (traces, ledgers, verdicts, counterfactual diffs) is immutable once sealed (§11.3); there is no deletion path.
- The campaign report has a required section **"Counterevidence and null results"** that appears *before* the positive-results section.
- Any analyst claim in the report that is not supported by a cited artifact path is a protocol violation (protocol [4] artifact contract).
