## Q1 — Does A9 fix M-1 structurally? (YES for the code path; NO as literally specified)

Confirmed the defect is exactly as M-1 states:
- M1 = `defect == oracle.true_cause and bool(target)` for `policy_rag_v1` (`score.py:251-257`), `true_cause="retrieval_omission"` (`oracle.json:5`).
- Both writers hard-code `"defect_class": None, "target_artifact": None` (`runner.py:376-377` offline; `runner.py:588-589` live). `Verdict` has no such fields (`models.py:215-231`); `FINDING_SCHEMA` has only `conclusion/statement/plan/evidence/confidence/executable` (`investigators.py:154-160`). So `M1(S0)=M1(S3)=M1(S4)≡0` by construction, and Δ is a task-interface artifact. Confirmed.

A9.2.1/2 (add the fields, thread the arm's *own* diagnosis to both writers) **does** remove the structural code-path asymmetry: after the change every arm has a code path to a non-null field, so M1(S0/S3/S4) *can* be non-zero. That part of the design is sound.

**But A9.2.1 is not implementable as literally written.** It requires a defect instruction "byte-identical to the defect instruction already registered for S5's RESOLVE." **No such registered instruction exists.** S5's RESOLVE prompt merely says `"...confidence, defect_class, target_artifact, statement, evidence_cited..."` (`orchestrator.py:543-551`) — it names the field but registers **no vocabulary**. The taxonomy `retrieval_omission | policy_conflict | judge_stale | generation_error | data_error | none` appears **nowhere in `src/`** (I grepped the whole tree). The only place `retrieval_omission` is emitted is the fixture's canned payload (`fake.py:60-67`).

Consequence — M1's *only* hard bet is the exact string `defect_class == "retrieval_omission"` (target_artifact only needs `bool`, `score.py:256`). If the shared instruction carries **no** taxonomy (to honor A9.2.3/A9.2.5 "no S5 change"), then *both* arms must free-guess that exact token from a prompt that never names it → both arms → ~0 for a **lexical** (not scientific) reason → Δ CI ⊇ 0 → NOT_SUPPORTED, and the campaign produces no finding. If the shared instruction **does** carry the taxonomy, it must be inserted into S5's RESOLVE, which changes S5's RESOLVE prompt bytes and *does* change S5 behaviorally (it gains the taxonomy it lacked) — directly contradicting A9.2.3/A9.2.5. **A9.2.3's "provably the same text across arms" and A9.2.5's "no S5 behavioral change" are not jointly satisfiable.** This is the load-bearing defect of the design (→ C1, C2).

**Residual interface asymmetries that would push comparators to ~0 for reasons other than "the task is harder":**
1. **Task-framing mismatch.** S4/S3/S0's defect question is appended to the numeric role-method prompt (`_ROLE_METHOD`, `investigators.py:164-186`: Cohen's d / t-test / RR on `mean_*/events_*` — fields this case does not have, so the method yields "insufficient data"). S5's RESOLVE is a *pure* diagnostic prompt (hypothesis + evidence + "name the defect", `orchestrator.py:534-585`). So the *defect block* is identical, but the *surrounding task* is not: S4's defect emission is structurally diluted by a mismatched numeric framing. (→ C6.)
2. **"First-non-null" is a label, not the same rule.** S5's first-non-null iterates fixed `AGENT_IDS` (`alpha,beta,gamma`, `orchestrator.py:539,564-568`) over per-hypothesis evidence where `alpha` = H_R sees the I_R evidence. S4/S3/S0's "first-non-null across committed findings" iterates the strategy's agent order over *shared-base-data* findings. Same word, different information and order. (Note only; see Q2.)

## Q2 — S5's richer evidence: confound or treatment? (The pivotal question)

**(a) It is the TREATMENT, not a confound — but only if the claim is kept to the mechanism bundle, not to "autonomy."**
The defensible contribution in `PRIOR_ART_NOVELTY_GATE.md` ("evidence-escrow + prequential counterfactual investigation … verified SimpleAudit interventions") is *precisely* that S5 runs counterfactual interventions and diagnoses from their verified outcomes, while S4 does not. A8 already removed the executor confound (same `LLMConfig`/model), so the intervention-evidence gap is the mechanism under test, not a hidden confound. **However**, Δ bundles three factors at once (escrow/decentralization vs. open-sharing, counterfactual interventions vs. none, pre-outcome per-hypothesis commitment vs. none). M1's difference is *dominated* by the intervention/identifiability factor, so a P1-SUPPORTED does **not** establish "decentralized autonomy improves diagnosis" — it establishes "running the counterfactual interventions improves diagnosis *on this seeded case*." The application must attribute Δ to the counterfactual-intervention mechanism (identifiability), not to autonomy in the abstract, and must not overclaim (→ C7).

**(b) Can S4 plausibly diagnose `retrieval_omission` from base data + deliberation alone? No — not *validly*. And that is the point.**
The strategy arms receive, via `to_prompt_block` (`isolation.py:43-70`) + `load_arm_claim` (`case_loader.py:158-173`): `test_prompt`, `policy_docs` (contains the current 30-day v2), `base_retrieval` (serves the stale 14-day v1), `order`, `base_policy_conflict`, `base_judge_reference_days=14` (`case.json`). Critically, **both** the base retrieval *and* the base judge reference point at 14 days. So from base data alone, `retrieval_omission` and `judge_stale` are **causally confounded / non-identifiable** — exactly why the counterfactual design exists: I_R (fix retrieval → target changes) vs. I_J (fix judge → output byte-identical, verdict flips) is what *disambiguates* which factor drives the target (`oracle.json` `expected_arm_outcomes`, I_P byte-identical rules out policy conflict). Therefore a *correct causal* diagnosis of `retrieval_omission` is **identifiable only via the interventions S5 runs**. If S4 scores M1≈0, that is a **valid scientific result** (the treatment supplies identifiability the baseline lacks) — *not* an artifact, and *not* "starvation."
**BUT** this valid result is currently *confounded* with the lexical artifact of (a): because `retrieval_omission` is never in S4's prompt (Q1), S4 may *substantively* identify "stale retrieval omitted the current doc" yet still score 0 for not emitting the exact token. The canary (Q3) does not separate these. So until the shared taxonomy is present (C1), "S4 M1≈0" cannot be read cleanly as "interventions matter" — it could be "S4 couldn't guess the word." (→ C1, C7.)

**(c) What the application must disclose (so an outside reviewer cannot read P1 either way):**
1. **Mechanism attribution (not autonomy):** state that Δ isolates the *counterfactual-intervention identifiability* mechanism, not decentralization per se; the comparison is S5 (escrow + local task choice + interventions) vs. S4 (open-sharing, no interventions).
2. **Base-data non-identifiability as a *case design property*:** state explicitly that in `policy_rag_v1` the retrieval factor and the judge factor are confounded in the base case, so the true cause `retrieval_omission` is not identifiable without the intervention the treatment provides. This is what makes S4's low M1 a *designed* identifiability gap, not evidence deprivation.
3. **M1 is a 5-way root-cause classification, not open-ended identification:** disclose that the shared registered taxonomy makes M1 a pick-from-`{retrieval_omission, policy_conflict, judge_stale, generation_error, data_error, none}` test, and that the scorer is an *exact* string match on `retrieval_omission` (`score.py:256`) — so a comparator that identifies the cause in different words scores 0. Name this as a known limit of M1's discriminative power.
4. **S5's token is partly label-availability:** S5's correct token is reinforced by the intervention arm being *named* `I_R_retrieval_fix` (so "retrieval" is the salient cause) and, pre-A9, by the fixture; disclose that S5's RESOLVE now carries the explicit taxonomy (C2) which slightly favors it.
5. **Single seeded case, no generalization:** tie to the novelty gate ("controlled case, not a real-world finding"); P1 certifies superiority at δ=0 on *this* case only (A1.8), no "autonomy beats central workflows" claim.

## Q3 — Canary sufficiency (A9.2.4)

- **Is all-null the right degenerate trigger?** For *interface-broken* (the M-1 regression: writers still null), yes — all-null is the correct signature that "the field is absent." Good as defense-in-depth.
- **But it is keyed on the wrong set.** A9.2.4 fires only if **all** runs across {S4 ∪ S3 ∪ S0} are null ("at least one S4/S3/S0 run … non-null"). The P1 estimand is **S5−S4 only**; S3/S0 are not in it. If **S4 is all-null but S3 has one non-null**, the aggregate canary *passes* yet M1(S4)≡0 → the exact false-positive SUPPORTED that M-1 forbids still occurs. The judge's own required-fix (#3) asked for "at least one comparator run in **each** of S4/S3/S0" (per-arm). The build must key the P1 canary on **S4 specifically** ("≥1 S4 primary run with non-null `defect_class` **and** `target_artifact`"). (→ C3, BLOCKING.)
- **Partial-null (some comparator runs null, some not):** correctly *not* degenerate — an LLM abstaining/nulling a field is expected. The all-null trigger already tolerates this. But it must be *per-arm* (each of S0/S3/S4), so a single all-null arm is caught, not masked by its siblings. (→ C3.)
- **Does it distinguish "non-null-but-inevitably-wrong" from "degenerate"?** **No — and it cannot, by construction.** The canary is binary on null-ness; a comparator that emits a non-null *wrong* cause (or the right cause in different words) is exactly what it lets through, and P1 can read SUPPORTED. This is acceptable *only* if the shared taxonomy is present (so "wrong" means genuinely-wrong cause = a valid scientific outcome). Without C1, a non-null-but-lexically-wrong S4 is indistinguishable from a healthy comparator and the false-positive path stays open. So the canary closes the *field-absent* regression only, not the *task-unwinnable* validity problem. (→ C1/C3.)

## Q4 — No estimand drift

Confirmed invariant, *subject to two guards*:
- M1 definition `_diagnosis_correct` (`score.py:251-257`) is untouched by A9; the estimand S5−S4, the `decision_branch` strict inequalities (`score.py:412-420`), the 10,000-resample paired-index bootstrap (`score.py:517-518,536-550`), the A1.3 rule string (`score.py:554-570`; len 1224, sha256 `766f4eb9…`), the 20-run decision, threshold, envelope/ceiling/seeds/counts — all unchanged. A9 changes only the *input* to M1 for comparators (hard-coded null → the arm's own field). This matches A9.2.5. **The design's non-change claim is correct on the estimator.**
- **Guard 1 (drift risk): the canary must be a *veto*, not a *filter*.** If the build implements the canary by *dropping* null comparator runs from `s4m` and recomputing the mean/CI on the survivors, it changes the denominator/estimand and the bootstrap — silent drift. It must instead set `P1.decision="m1_interface_degenerate"` (a void, distinct from SUPPORTED/FALSIFIED/NOT_SUPPORTED and from `no_valid_runs`) *before* the bootstrap, leaving `s4m` untouched. (→ C4, MUST.)
- **Guard 2 (drift risk): do not start exact-matching `target_artifact`.** M1 for `policy_rag_v1` scores `bool(target)` only (`score.py:256`). If wiring "the arm's real target_artifact" is used to also *exact-match* an oracle artifact, M1's definition changes. Keep `defect==true_cause and bool(target)`. (→ C5, MUST — re-verify via sha/tests, mirroring the A1.3 re-pin.)

## Q5 — Implementation risk to the design's claims

1. **Threading through `Verdict` — safe for A1.3 and A8.** `Verdict` is a plain dataclass (`models.py:215-231`); adding two `Optional` fields touches neither the A1.3 rule string (lives in `score.py`) nor the A8 parity guard (keys on `run_metadata.model/offline_arm`, `score.py:446-462,492`). **Confirmed: no risk to either.**
   - **Wiring gap (must be specified):** `_commit` builds the commitment payload from a *fixed* key list `{"conclusion","statement","plan","evidence","confidence","executable"}` (`strategies.py:106-113`) — it does **not** carry `defect_class/target_artifact`. So "first-non-null across committed findings" would read nulls. The aggregation must read from the **finding dicts** in `StrategyResult.evidence[*].finding` (populated by `_ev`, `strategies.py:84-104`), and the aggregate must be *computed* (first-non-null) and attached to `ArmResult`/`Verdict` in `_finalize`/`arm.run` — it is not a raw passthrough. Also `StrategyResult.to_dict` (`strategies.py:63-77`) drops evidence, so the writer must consume the aggregate, not `to_dict`. (→ C8, MUST.)
2. **Shared-instruction constant vs. S5 RESOLVE prompt bytes.** S5 RESOLVE currently has no defect block, so "sourcing it from the shared block" **will change S5's RESOLVE prompt bytes**. Existing tests pin only *substrings* — `test_prompt_evidence.py:84` (evidence header), `:87` (`_BLOCK_FOOTER = "Respond with JSON containing conclusion"`), `:317` (`evidence_cited (...)`). So inserting the taxonomy *before* the footer and preserving those substrings keeps the suite green. **But** this makes A9.2.5's "no S5 behavioral change" and A9.2.3's "no behavioral change to S5" **false** — S5 gains an explicit defect taxonomy it previously lacked (which can only raise S5's M1). The amendment text must be corrected to say S5's RESOLVE *prompt gains the registered taxonomy* while S5's evidence construction / first-non-null rule / extraction are unchanged. (→ C2, BLOCKING — this is where Q1 and Q5 collide.)
3. **FINDING_SCHEMA fields vs. oracle-leak / evidence-contract tests.** The shared block's taxonomy words (`retrieval_omission|policy_conflict|judge_stale|generation_error|data_error|none`) are **not** in `EVIDENCE_FORBIDDEN_SUBSTRINGS` (`orchestrator.py:52-61`; that list holds field names like `true_cause`, not values) — so the S5 guard is not tripped. Note, though, that the strategy path **has no** oracle-leak guard today; A9.2.1's "guard is reused" is a *new* guard on the strategy finding prompt — acceptable (more safety) but it is a change to that path. Listing the 5 candidate labels does not leak ground truth (it's a menu, not the answer), but it does convert M1 into a 5-way classification (disclose per Q2(c)). The `FakeLLMClient` six-arm re-pin (A9.3) should still hold because the fake returns `retrieval_omission` regardless of prompt (`fake.py:60-67`) — but re-run the suite to be sure no exact-prompt-byte assertion exists beyond the three substring pins. (→ C5/C9.)

### Bottom line
A9 is the right shape of fix and removes the structural code-path asymmetry, but the design as registered contains one hard internal contradiction (C1/C2: there is no S5-registered defect vocabulary, so "byte-identical + no S5 change" cannot both hold) and one wrong-scoped canary (C3: keyed on any-of{S0,S3,S4} rather than the P1 comparator S4). Until C1–C3 land (BLOCKING) and C4–C8 are satisfied in code and application text, A9 does not yet deliver a *defensible* P1 — it risks swapping one asymmetry (comparators can't emit the field) for another (comparators can't emit the *word*, or are nudged to ~0 by a mismatched framing), which the all-null canary would not catch. Fix those and the P1 becomes a valid, mechanism-attributed identifiability result on a single seeded case.
